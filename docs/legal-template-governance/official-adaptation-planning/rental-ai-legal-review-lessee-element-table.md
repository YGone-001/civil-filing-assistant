## 1. 结论摘要

1. **承租人场景应作为独立模板或明确的原告角色分支处理，不应直接套用当前出租人追索欠租模板。** 官方表按出租人／承租人分流：承租人可主张交付房屋（第 3 项）和返还押金（第 8 项），而当前模型只覆盖出租人的欠租、违约金、解除和腾退请求。
2. **官方要素式表格不宜整体照搬，宜作为“要素核对清单”嵌入现有叙述式初稿。** 对普通用户而言，完整 12 项请求表＋15 项事实表会显著增加填写负担；更合适的做法是保留叙述式起诉状，按请求类型渐进式补充关键要素。
3. **承租人模板的最低可行范围**应以官方表第 3、8 项和共同项第 4、9–12 项为骨架，至少覆盖：交付房屋、返还押金、确认／请求解除、实现债权费用、诉讼费用、标的总额。其他费用和损失赔偿可作为可选扩展，不应默认生成。
4. **事实完整性优先于模板完整度。** 承租人是否实际支付押金、房屋是否交付、是否已返还、押金是否已抵扣、合同是否解除，都必须由用户明确确认；未确认时只能使用“待核对”或中性表述，不能推断。
5. **该审阅不构成法律意见、映射批准、工程授权或发布批准。** 承租人模板和要素表改造仍需单独的工程范围授权、DOCX 回归和发布决策。

## 2. 承租人场景分析

### 2.1 官方表的承租人分支

官方表在诉讼请求部分明确：原告为出租人时填写第 1、2、5、6、7 项；原告为承租人时填写第 3、8 项；第 4、9–12 项为共同项。

承租人分支的核心请求：

- **第 3 项：交付房屋。** 适用于出租人未按约交付租赁物，承租人请求实际交付的情形。
- **第 8 项：返还押金。** 适用于承租人已支付押金，合同终止或解除后出租人未返还的情形。
- **共同项第 4 项：请求解除合同。** 承租人也可主张解除，但解除基础可能是出租人违约（如未交付、房屋不符合约定）而非欠租。
- **共同项第 9–12 项：实现债权费用、诉讼费用、其他请求、标的总额。**

### 2.2 当前模型的差距

当前 `RentalCaseModel` 的事实与请求以出租人追索欠租为中心：

- 请求：解除（仅请求解除状态）、欠租、违约金、腾退返还、诉讼费。
- 事实：出租人交付房屋、承租人欠租、催缴、合同状态、房屋返还。

因此，直接让承租人使用当前模型会产生至少三类错误：

1. 把承租人写成“欠租被告”，与实际诉讼地位相反；
2. 无法提出交付房屋和返还押金请求；
3. 事实叙述默认出租人已交付房屋、承租人未支付租金，可能与承租人主张相反。

### 2.3 建议的承租人最小字段集

| 字段 | 用途 | 必要性 |
|---|---|---|
| 原告角色 | 出租人／承租人 | 必填，决定模板分支 |
| 租赁合同及房屋信息 | 合同签订、房屋地址、租期、租金 | 必填 |
| 押金是否支付、金额、支付日期 | 返还押金请求的基础 | 承租人主张押金时必填 |
| 押金是否已返还、返还金额、抵扣情况 | 确定未返还余额 | 承租人主张押金时必填 |
| 房屋是否交付、交付日期 | 交付房屋请求的基础 | 承租人主张交付时必填 |
| 房屋是否符合约定、未交付原因 | 交付请求的事实依据 | 可选但建议 |
| 合同状态、解除方式、解除日期 | 共同项第 4 项 | 视请求而定 |
| 催告／通知及送达情况 | 解除或交付请求的程序事实 | 可选但建议 |
| 损失及其他费用 | 扩展请求 | 可选，默认不生成 |

### 2.4 建议的承租人请求逻辑

- **交付房屋**：仅在用户确认“出租人未交付”且承租人仍要求交付时生成；如果房屋已交付或用户未确认，不生成。
- **返还押金**：仅在用户确认“押金已支付”且“未返还／未足额返还”时生成；金额应为用户确认的未返还余额，不自动从租金中抵扣。
- **解除合同**：区分协商解除、通知解除、直接起诉主张解除和租期届满；解除日期有争议时，由用户确认是否单列确认请求。
- **损失赔偿**：默认不生成；如用户主动主张，需求填写损失项目、金额或计算方式、证据，并核对与押金、租金、占有使用费的重叠。
- **诉讼费用、实现债权费用、标的总额**：作为共同项处理；标的总额由用户确认，不静默计算。

### 2.5 法律与程序风险提示

- 交付房屋请求的基础是出租人的交付义务；需核对合同约定、房屋现状、交付通知和实际占有情况。
- 押金返还需核对合同约定、支付凭证、扣减项目、结算记录和抵销主张；押金与欠租、违约金、损坏赔偿可能重叠。
- 承租人主张解除时，解除基础和通知程序与出租人因欠租解除不同；不能复用“欠租催告”事实。
- 房屋租赁合同纠纷通常涉及不动产所在地管辖；如存在仲裁条款，需另行核对仲裁协议的效力和范围。
- 以上为一般性分析，具体适用取决于合同、证据、目标和法院；本文不构成法律意见。

## 3. 官方要素式表格分析

### 3.1 官方表的结构价值

官方表的价值不在于“必须逐格复制”，而在于它提供了可核对的要素清单：

- 诉讼请求 12 项，区分出租人／承租人分支；
- 事实与理由 15 项，覆盖合同签订、主体、标的物、租期、租金、费用、违约、解除条件、交付、押金、支付历史、欠租、其他说明、请求依据和证据清单；
- 约定管辖和诉前保全；
- 对纠纷解决方式的意愿；
- 签署栏。

这些要素可以帮助当前叙述式模板发现遗漏，但不意味着普通用户必须填写全部栏目。

### 3.2 三种采用方式比较

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 完整复制官方要素表 | 与官方结构最接近 | 开发量大、用户负担重、容易让普通用户误以为必须逐项填写 | 不推荐作为默认 |
| 完全保持叙述式，不补要素 | 简单 | 容易遗漏押金、交付、标的总额、管辖等关键事项 | 不推荐 |
| 叙述式＋要素核对清单 | 保留可读性，按需补充关键要素 | 需要设计渐进式提示和完整性检查 | **推荐** |

### 3.3 建议的混合方案

1. **保留叙述式起诉状**作为普通用户的主路径。
2. 在租赁页增加“要素核对”区域，只对当前请求相关的要素提问：
   - 出租人：欠租期间、违约金计算、解除、返还、占有使用费、水电费、押金抵扣；
   - 承租人：交付房屋、押金返还、解除、损失；
   - 共同：管辖约定、诉前保全、标的总额、证据清单引用。
3. 对未填写的可选项显示“未填写／不主张／待核对”，不自动生成肯定性事实。
4. 在导出前显示“要素完整性检查”，列出缺失项和风险提示，但不阻止用户导出（除非缺失项属于必填）。
5. 不复制官方表格文字；只使用栏目名称和结构作为核对参考。

### 3.4 对当前产品的具体建议

- **原告角色**：新增 `plaintiff_role`（出租人／承租人），作为租赁模板的第一分支；未选择时阻止生成。
- **承租人模板**：新增 `LesseeRentalCaseModel` 或在现有模型中按角色分支；建议独立模型，避免出租人逻辑污染承租人请求。
- **押金字段**：押金金额、支付日期、是否返还、未返还余额、抵扣说明；未确认时不生成返还请求。
- **交付字段**：房屋是否交付、交付日期、未交付原因、是否仍要求交付；未确认时不生成交付请求。
- **要素核对**：在租赁页或导出页增加只读清单，显示当前请求对应的官方要素是否已覆盖；不改变现有叙述式文书结构。
- **范围控制**：首版承租人模板只覆盖交付房屋、返还押金、解除、诉讼费、标的总额；其他费用和损失赔偿另行决策。
